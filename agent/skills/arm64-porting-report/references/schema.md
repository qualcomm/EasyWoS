# x64-to-arm64-porting YAML Schema Reference

## Schema Identity

```yaml
schema: x64-to-arm64-porting
```

This is the canonical schema name. Every report generated by the `arm64-porting-report` skill must include this exact value.

## Full Field Specification

### Top Level

| Field | Type | Required | Description |
|---|---|---|---|
| `schema` | string | yes | Must be `x64-to-arm64-porting` |
| `description` | block scalar | yes | Overall description of the porting task |
| `porting_items` | sequence | yes | One or more porting item entries |

### porting_items Entry

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | Unique kebab-case identifier (e.g. `function-prolog`, `simd-accumulator`) |
| `title` | string | yes | Short human-readable title |
| `description` | block scalar | yes | Detailed description of the code section and why it needs porting |
| `source_architecture` | string | yes | `x86_64` |
| `target_architecture` | string | yes | `AArch64 (ARM64)` |
| `calling_convention` | string | yes | `Microsoft x64 (Windows)` or `AAPCS64 (Linux)` |
| `file_path` | string | yes | Relative path to the source file |
| `code_range` | string | yes | Line range. Single range `21-30`, OR comma-separated multi-range string `"10-12, arch/x86/crc32_pclmulqdq_tpl.h:140-220"` when the wrapper line range and the included template body must both be in scope (see SKILL.md Rule A — Template-Body Recursion). |
| `semantics` | block scalar | yes | Numbered list of what the original code does, one step per operation |
| `constraints` | sequence | yes | ARM64-specific rules and constraints the implementer must follow |
| `register_mapping` | mapping | yes | x64 register -> ARM64 register with inline comments |
| `intrinsic_equivalents` | mapping | no | SSE/AVX intrinsic pattern -> NEON equivalent; include only for SIMD code |
| `target_feature` | string | no | ARM64 hardware-feature variant the item targets (e.g. `armv8-a+crc`, `armv8.2-a+crc+crypto+sha3`, `armv8-a+sve2`). Required when the same x86 kernel maps to multiple ARM64 variants (CLMUL/AES/SHA/VNNI dispatch); see SKILL.md "Architectural Variants". |
| `variant_group` | string | no | Group identifier shared by all items that target the same x86 source bytes via different ARM64 hardware features. Items in the same `variant_group` MAY have overlapping (or identical) `code_range`; their `id` values MUST share the variant_group as a prefix. |

## `code_range` Syntax

The matcher accepts three forms:

| Form | Example | Meaning |
|---|---|---|
| Single range | `21-30` | Lines 21 through 30 inclusive of the item's `file_path` |
| Multi-range, same file | `21-30, 47-61` | Lines 21–30 plus 47–61 of the item's `file_path` |
| Multi-range with cross-file `path:` prefix | `"10-12, arch/x86/crc32_pclmulqdq_tpl.h:140-220"` | Lines 10–12 of the item's `file_path` AND lines 140–220 of the secondary file. The secondary path is resolved relative to the YAML's directory (same rule as `file_path`). |

Cross-file ranges are required when the wrapper file is thin and the SIMD body is in an `#include`d template header. The wrapper file remains the item's primary `file_path` for traceability; the secondary range adds the body so the matcher's regex sees the actual intrinsic calls.

## Architectural Variants — Schema Pattern

When the same x86 SIMD kernel can map to multiple ARM64 implementations selected at runtime by feature detection, the schema requires emitting one `porting_item` per ARM64 variant under a shared `variant_group`. Below is the canonical shape; see SKILL.md's "Worked Example — CRC32 Wrapper + Template Body + Two ARM64 Variants" for a fully populated instance.

```yaml
porting_items:

  - id: <group-prefix>-<variant1-tag>
    title: <X86 kernel name> (→ <variant1 ARM64 description>)
    variant_group: <group-prefix>
    target_feature: armv8-a+<feature1>
    file_path: <same as variant2>
    code_range: <same as variant2>           # overlap intentional; allowed by Rule #6
    # ... semantics identical, constraints + intrinsic_equivalents differ ...

  - id: <group-prefix>-<variant2-tag>
    title: <X86 kernel name> (→ <variant2 ARM64 description>)
    variant_group: <group-prefix>
    target_feature: armv8.2-a+<feature1>+<feature2>
    file_path: <same as variant1>
    code_range: <same as variant1>
    # ... different ARM64 instruction family ...
```

Common variant groups in real codebases:

| variant_group example | x86 kernel | variant 1 (`target_feature`) | variant 2 (`target_feature`) |
|---|---|---|---|
| `crc32-vpclmulqdq` | `crc32_vpclmulqdq_avx512` | `armv8-a+crc` (hardware CRC32 instructions) | `armv8.2-a+crc+crypto+sha3` (PMULL + EOR3 fold) |
| `aes-encrypt` | `_mm_aesenc_si128`-based loop | `armv8-a+crypto+aes` (vaeseq_u8) | `armv9-a+sve2+aes` (svaese_u8 — when SVE2 in scope) |
| `sha256-rounds` | `_mm_sha256rnds2_epu32` | `armv8-a+crypto+sha2` (vsha256hq_u32) | `armv8.2-a+crypto+sha3` (where applicable) |
| `dpbusd-vnni` | `_mm512_dpbusd_epi32` | `armv8.2-a+dotprod` (vdotq_s32) | `armv8.6-a+i8mm` (vusmmlaq_s32) |

## Canonical Example

```yaml
schema: x64-to-arm64-porting
description: |
  Porting report for compute_sum: two sections from src/compute_sum.asm
  require translation — a standard Windows x64 function prolog and an
  SSE2 floating-point accumulation loop.

porting_items:

  - id: function-prolog
    title: Function Prolog (Stack Frame Setup)
    description: |
      Standard Windows x64 function prolog that sets up a stack frame,
      saves non-volatile registers, and reserves local variable space.
      Must be translated to ARM64 frame pointer convention and
      callee-saved register preservation rules.

    source_architecture: x86_64
    target_architecture: AArch64 (ARM64)
    calling_convention: Microsoft x64 (Windows)

    file_path: src/compute_sum.asm
    code_range: 21-30

    semantics: |
      1. Save old frame pointer (rbp) to stack
      2. Establish new frame pointer
      3. Allocate 32 bytes of local/shadow space
      4. Preserve callee-saved registers: rbx, rsi, rdi
      5. Move parameters from volatile registers (rcx, rdx) into
         non-volatile registers for use across function calls

    constraints:
      - Stack must remain 16-byte aligned on ARM64
      - ARM64 uses x29 (FP) and x30 (LR) as frame pointer and link register
      - Callee-saved registers on ARM64 (AAPCS64): x19-x28, d8-d15
      - Parameters arrive in x0, x1 (not rcx, rdx)
      - STP/LDP instructions should be used for paired register save/restore

    register_mapping:
      rcx: x0   # first integer parameter
      rdx: x1   # second integer parameter
      rbp: x29  # frame pointer
      rsp: sp   # stack pointer
      rbx: x19  # callee-saved (mapped)
      rsi: x20  # callee-saved (mapped)
      rdi: x21  # callee-saved (mapped)
      rax: x0   # return value

  - id: addition-logic
    title: SIMD Addition with Scalar Accumulation
    description: |
      An x64 loop body that uses SSE2 to perform packed single-precision
      floating-point addition, then horizontally sums the result into a
      scalar accumulator. Must be translated to ARM64 NEON equivalents.

    source_architecture: x86_64
    target_architecture: AArch64 (ARM64)
    calling_convention: Microsoft x64 (Windows)

    file_path: src/compute_sum.asm
    code_range: 47-61

    semantics: |
      1. Loop: load 4 consecutive floats from memory (unaligned)
      2. Accumulate via packed float addition (SIMD 4-wide)
      3. Advance loop index by 4, branch if more elements remain
      4. After loop: horizontal reduction of 4-lane accumulator to scalar
         using high-to-low move, packed add, shuffle, and scalar add

    constraints:
      - ARM64 NEON uses 128-bit V registers (v0-v31) with float32x4_t lanes
      - No direct equivalent of movhlps; use EXT or DUP+FADDP
      - NEON FADDP (pairwise add) is preferred for horizontal reduction
      - LDR q-form loads are always naturally aligned on ARM64; use LD1 for
        potentially unaligned access
      - ARM64 loop control uses CBZ/CBNZ or CMP+B.cc (no direct JB equivalent)
      - NEON addps equivalent: FADD Vd.4S, Vn.4S, Vm.4S

    register_mapping:
      xmm0: v0   # SIMD accumulator (float32x4)
      xmm1: v1   # SIMD scratch register
      rsi: x0    # base pointer to float array
      rcx: x1    # loop index
      rdx: x2    # loop bound (count)

    intrinsic_equivalents:
      movups_load: vld1q_f32(ptr)
      addps: vaddq_f32(a, b)
      horizontal_sum: vaddvq_f32(v)  # ARMv8.2 single-instruction reduction
```
